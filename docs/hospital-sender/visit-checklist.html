AMCGH visit checklist — automatic data sending

NSU × AMCGH lung cancer imaging research · prepared 10 November 2026

What we want to set up. A small program on one hospital computer. Every 3 days it collects the new X-ray, CT and report files, puts them in one zip file, and sends that file securely over the internet to the NSU research server. It only reads files; it never changes, moves or deletes anything. Hospital staff do not need to do anything after it is set up. This replaces carrying files to NSU on an SSD.

Why we are asking. We have not yet seen the hospital's software or computers, so we cannot build it correctly without these answers. Some questions we think we already know — those show Our guess. Please still confirm them.

1. People and permission

  1. 1.1Who in hospital IT will be our contact for this program?MUST
    Someone has to install it, and someone has to call if it stops.
  2. 1.2Who must approve installing an outside program that sends data out of the hospital? Is there a written form or policy?MUST
    Some hospitals need IT head, director or data-protection approval first.
  3. 1.3Does the ethics approval and the MoU cover sending data automatically over the internet (not only by hand / SSD)?MUST
    The approval may name how data is moved.
    Our guess: ethics approval is obtained; whether it names the transfer method is not known.
  4. 1.4Should it send files for all patients, or only patients in the study?MUST
    If only study patients, we need a rule to pick their files (see 6.3).
  5. 1.5Does the hospital need to see or check the program's code before it is installed?
    We can share the code and explain it.

2. The hospital software

  1. 2.1What is the name of the hospital's main software (patient records, billing, lab, radiology)? Which company made it, and which version?MUST
    Tells us what it can export and whether the company can help.
  2. 2.2Is it a program installed on each PC, or a website used in a browser? Is it on a hospital server or online (cloud)?
  3. 2.3What is it built with (programming language) and which database does it use (SQL Server, MySQL, Oracle, other)?
    If we ever read from it directly, we must know this. Their IT or the vendor will know.
  4. 2.4Can it export or save reports to a folder by itself (automatic export)? In what format (PDF, Word, Excel, CSV)?MUST
    If yes, our program just picks up that folder — the simplest and safest way.
  5. 2.5Does it have any connection for other software: API, HL7, FHIR, or a read-only database login?
  6. 2.6Who is the vendor's support contact, and does the hospital have a support contract?

3. Scans (X-ray, CT, MRI)

  1. 3.1Is there a PACS (scan storage server)? Name and company?MUST
  2. 3.2Which X-ray, CT and MRI machines are used (brand, model)? Digital X-ray or film?
    Film X-rays have no digital file; their scale for tumour size is lost.
  3. 3.3In what format are scans saved: DICOM (.dcm), JPG, or other? Are they compressed?MUST
    The research needs original DICOM files; they keep the true size (pixel spacing) for measuring tumours in cm.
    Our guess: DICOM. Not confirmed.
  4. 3.4Can the PACS automatically copy (forward / "DICOM send") new chest scans to a folder or to another PC?
    If yes, the PACS feeds a folder and our program sends that folder.
  5. 3.5About how many chest X-rays and chest CTs are done per day? How big is one CT study (MB/GB)?MUST
    3 days of CT can be several GB; this decides internet needs.

4. Reports

  1. 4.1How are radiology reports written: typed in the hospital software, typed in Word, or handwritten and scanned?
  2. 4.2Where are reports saved, and in which format?
  3. 4.3Do clinical notes (treatment, chemo/radiotherapy, follow-up) exist as files too, or only on paper?
    Later research phases need treatment and outcome data.

5. The files on the PC

  1. 5.1Which computer holds the files? Its name, and where it is.MUST
  2. 5.2Exact folder path(s) (e.g. D:\Reports). Are files sorted into subfolders (by date, by patient)?MUST
  3. 5.3How are files named? Does the name include the patient ID (RC number), date, or scan type?MUST
    This is how we match a scan to its report and to the patient.
  4. 5.4Are the files on that PC itself, or on a shared network drive / server?
  5. 5.5Are files ever edited, renamed, moved or deleted after they are first saved? Are old files cleared out?
    Corrected reports are sent again; files cleared too soon could be missed.
  6. 5.6How much new data appears per day (number of files, total MB/GB)?

6. Patient identity and privacy

  1. 6.1Confirm: the files do not contain patient names — including inside the scan files (DICOM "Patient Name" field) and report headers.MUST
    DICOM files often carry the name inside, even when the file name does not.
    Our guess: no names in the files (as we were told). Please check one scan and one report together.
  2. 6.2What other details are inside: phone, address, date of birth, national ID?
  3. 6.3Which ID links a scan, its report and the patient: RC number, accession number, other?MUST
    Our guess: RC number (RC + digits), as used in our capture app.
  4. 6.4Is the scan date and report date inside the files?
    The research compares baseline CT with later X-rays by date.

7. The computer

  1. 7.1Windows version (7, 10, 11) and 32- or 64-bit?MUST
    Windows 7 or 32-bit changes how we build the program. Check with Win + R → winver.
    Our guess: Windows 10 or 11, 64-bit.
  2. 7.2Is it switched on all the time, or turned off at night / weekends?
    Decides what time of day it sends.
  3. 7.3Can we get administrator rights to install it and add a scheduled task?MUST
  4. 7.4Which antivirus is installed? Does it block new programs?
  5. 7.5Free disk space (needs room for one zip, possibly several GB)?
  6. 7.6Is there a UPS / are there frequent power cuts?

8. Internet and network

  1. 8.1Does that PC have internet? Is it allowed to send data outside the hospital?MUST
  2. 8.2Upload speed (run speedtest.net on that PC) and any monthly data limit?MUST
  3. 8.3Is there a firewall or proxy? Are some websites blocked? Must the NSU server address be allowed first?
  4. 8.4Best time to send so the hospital network is not slowed (e.g. after 11 pm)?
    Our guess: night, around 11 pm.

9. Sending schedule and support

  1. 9.1Is every 3 days right? Should it ever send more often, or only on certain days?
    Our guess: every 3 days, checked once a day so a missed day catches up.
  2. 9.2Which file types should be sent, and which never (e.g. billing files)?
  3. 9.3From what date should it start (only new files from now, or older files too)?
  4. 9.4If it stops working, who at the hospital can we call? Is remote access (AnyDesk, TeamViewer) allowed for us to fix it?
  5. 9.5Does the hospital want a copy of what was sent, or a monthly summary?

Things to see and collect during the visit

  • Sit at the actual PC. Note its name and Windows version (winver).
  • Photo of the folder(s) in File Explorer, showing subfolders and how files are named.
  • Open one scan file and one report: check for patient names, phone, address. Photo with any name covered.
  • With permission, one sample of each file type with all patient details removed or a test patient — to build and test with.
  • Photo of the hospital software's export screen, if it has one, and its "About" screen (name, version).
  • Photo of the PACS screen and its name/version, if allowed.
  • Run speedtest.net on that PC; write down upload and download speed.
  • Check free space on each drive (This PC in File Explorer).
  • Count how many files appeared in one recent day, and their total size (folder → Properties).
  • Check whether a browser on that PC can open the NSU server address we give you (tests internet and blocking).
  • Get the IT contact's phone and email; agree on a date to install and test.
  • Ask for any written IT policy or approval form for outside software.

For the NSU team before go-live (not for the hospital)

  • Decide where the always-on NSU server runs. The current test link (lab PC + free ngrok) is not enough for months of multi-GB uploads.
  • Make sure the server has disk space for the expected GB per month (from 3.5 and 5.6).
  • Decide how SSD files already received will be joined with the files that arrive automatically.
